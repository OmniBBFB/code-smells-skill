# 独立代码坏味道审查

范围：仅本目录 code-smells 规则与 cases/case-01 至 case-23 的 sample.py。23 个案例独立审查，不跨案例推断共同领域；未读取父目录、答案、其他工作目录或历史。案例未修改。

覆盖：每个完整供应片段均按 S01—S23 筛选，并用完整六类规则核查明确候选及例外。没有证据的类别仅筛选未见候选，不机械列出。共5条确定发现；同一根因合并，重复/变化传播的次要标签保留在说明中。

局限：省略实现、未知调用者与外部类型不予补全。缺失上下文仅针对已出现候选列出；没有确定发现不表示完整仓库无问题。未运行案例、未查看历史，不断言过去修改频率。

## case-01

- **S06** — `cases/case-01/sample.py:6-14`
  证据：fee 在7-8行、days 在12-13行分别判断 shipment.kind 的 air/road；2行明确增加承运类型需要费用和时长。
  影响：新增承运类型需同步调整两个独立分派点，漏改会造成某能力拒绝该类型（当前结构风险）。
  最小建议：用一个承运类型到费用/时长的记录映射集中分派；仅当行为复杂时再用策略。

## case-02

- **S14** — `cases/case-02/sample.py:1-10`
  证据：2行明确 web_total 与 batch_total 为同一发票计价规则；3-5与8-10行重复小计、17%税及汇总。
  影响：同一税率或计价算法变化需同时修改两个入口，存在行为分叉风险。
  最小建议：提炼共同计价函数，由两个入口调用。

## case-04

- **S08** — `cases/case-04/sample.py:1-11`
  证据：Storage 第2行要求所有子类型无额外限制支持非空字节写入；ReadOnlyStorage 第7-8行拒绝所有写入；backup 第10-11行按父契约写入。
  影响：传入 ReadOnlyStorage 时 backup 的合法父类型操作失败；客户端需辨认子类型。
  最小建议：把读写能力分开，让只读类不继承要求写入的 Storage；复用实现时用组合。

## case-07

- **S03** — `cases/case-07/sample.py:1-10`

## case-10

- **S20** — `cases/case-10/sample.py:2-15`
  证据：钱包2行规定余额变化必须经 debit 补流水；7-11行统一校验、余额更新和流水；Payment 第15行直接更改 _balance。
  影响：现有 pay 路径绕过金额校验且没有写入流水，破坏明确的余额/流水一致性约束，并依赖内部表示。
  最小建议：Payment.pay 调用 wallet.debit(amount)，由钱包维护完整操作。
