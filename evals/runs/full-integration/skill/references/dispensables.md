# 可清理的问题：S13—S18

删除或合并建议应有真实使用与边界证据。审查只读；候选不意味着可以立即删除代码。

## S13 注释 · Comments

- **定义：** 注释被用来补偿晦涩的命名、分支或职责，使代码与解释形成两份需同步维护的实现知识。
- **候选信号：** 大段文字逐步翻译难懂代码；注释给无意义变量或魔法值解释业务含义；注释段落实际上在划分可命名操作。
- **必要证据：** 同时阅读注释与实现，指出晦涩点及可通过命名、提炼或显式类型表达的语义。注释存在、数量多或文档长不构成证据。错误／过期注释可单独报告文档缺陷，不自动等同结构坏味道。
- **合理例外：** 解释设计理由、外部限制、安全假设、算法依据或不可见上下文；公共 API 文档、许可证和协议说明。
- **维护影响：** 读者依赖注释还原意图，代码变化可能令解释失真；明确哪段知识重复。
- **改善方向：** 改善名称、提炼语义操作或明确常量；保留“为什么”的说明，避免为了减少注释删掉必要背景。
- **上下文不足：** 只有注释看不到对应实现时无法判断其是否补偿结构，先索取或定位实现。

## S14 重复代码 · Duplicate Code

- **定义：** 同一知识或业务规则有多份独立实现，需保持一致却没有可靠的共同来源。
- **候选信号：** 相同计算、校验、控制结构或差异很小的方法；多份独立规则常量。
- **必要证据：** 比较至少两处完整逻辑及语义，确认它们表达同一知识；检查差异是否真正重要。文本相似、模板结构相同、测试预期与实现相同不充分。
- **合理例外：** 生成代码、刻意独立的测试期望、不同领域偶然相似的规则、具有清楚隔离依据的跨服务复制。
- **维护影响：** 同一规则变化需重复调整，可能行为分叉。
- **改善方向：** 提炼共同规则、参数化真实差异或引入共同算法。若变化方向独立，保留分离比错误抽象更好。
- **上下文不足：** 只有一处或不知道两个片段语义时保留判断，不能凭相似行数认定重复知识。

## S15 懒惰类 · Lazy Class

- **定义：** 独立类型没有足以抵偿额外对象、导航和维护成本的职责或边界。
- **候选信号：** 局部仅为传递一个已有值而建类；精简后几乎不剩行为；调用者需拆开包装才能继续操作。
- **必要证据：** 查看实例化、使用路径与契约，说明当前类型没有独立约束、语义或替换边界，并指出多余成本。类小、方法少、没有行为都不是单独证据。
- **合理例外：** 值对象、DTO、标记类型、异常类型、端口、受框架要求的类型或有实际隔离作用的适配器。
- **维护影响：** 阅读和修改需穿过没有收益的类型，重复同步包装接口。
- **改善方向：** 内联局部类型或合并职责，保留必要语义和公开兼容性。与中间人重合时合并报告，用实际根因选主标签。
- **上下文不足：** 不知道调用者、类型身份或框架用途时，明确尚未确认边界收益。

## S16 数据类 · Data Class

- **定义：** 承载领域状态的类缺少与状态紧密关联的业务行为，让客户端重建或绕过其规则。
- **候选信号：** 公开可变字段加 getter/setter；多个客户端校验、计算并修改同一对象的状态。
- **必要证据：** 确认它承担领域模型职责，查看至少一个外部规则或状态修改路径；指出应由谁维护的约束。只有字段、dataclass 或缺方法不充分。
- **合理例外：** DTO、消息、数据库投影、序列化记录、明确使用纯函数和集中规则的函数式模型、分离读写模型。
- **维护影响：** 规则散落在调用者，状态可进入非法组合；说明具体约束。
- **改善方向：** 把适当行为靠近数据或提炼集中策略，保护修改入口；不必把运输模型变成领域对象。
- **上下文不足：** 数据定义孤立出现、规则与边界未知时先核实用途，不根据无方法定罪。

## S17 死代码 · Dead Code

- **定义：** 在已确认的运行与入口约定下，代码无法到达、没有消费者或不影响所需行为，却仍增加维护负担。
- **候选信号：** 无条件 return 后的语句、已恒定排除的分支、无读取的计算结果、疑似无调用成员。
- **必要证据：** 对不可达代码说明控制流证明；对无调用成员，检查引用、导出、配置、框架注册及动态入口。限定证据适用范围；文本搜索无命中不能证明全局未使用。
- **合理例外：** 反射、插件、依赖注入、CLI／框架入口、外部公开 API、具有副作用的表达式、仍需兼容的迁移代码。
- **维护影响：** 读者误以为路径有效，修改或审查无用实现；区分代码死与业务能力暂时少用。
- **改善方向：** 在已证实范围内建议移除或隔离，并验证相关入口；审查阶段不执行删除。
- **上下文不足：** 缺少配置、导出或运行约定时标记疑似未使用，不能建议确定性删除。

## S18 推测性泛化 · Speculative Generality

- **定义：** 为未有证据支持的变化设计扩展机制，实际增加理解或配置成本，却没有当前契约或已知需求收益。
- **候选信号：** 私有流程中永不传入的回调、没人选择的策略配置、无法从现有入口使用的扩展层。
- **必要证据：** 查看扩展点调用者、公开性及配置／需求约定，证明当前额外机制缺少用途并指出真实成本。“只有一个实现”或“现在没用第二种”不充分。
- **合理例外：** 已承诺的插件 API、测试替身、多个可用配置、稳定端口、已确认但尚未接入的需求。
- **维护影响：** 读者需理解无法实际使用的变化点，错误的扩展轴约束后续设计。
- **改善方向：** 简化没有价值的私有扩展机制，保留有契约依据的边界；不要把“当前没有需求”推广为永不允许抽象。
- **上下文不足：** 看不到调用者、公开契约或扩展计划时，报告需查的用途，不臆测未来需求不存在。
