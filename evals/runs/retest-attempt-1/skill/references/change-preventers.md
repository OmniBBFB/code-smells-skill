# 阻碍修改的问题：S10—S12

这些诊断通常需要跨成员或跨文件比较。没有历史也可依据当前职责和规则分布判断潜在变化路径，明确标记为推断；实际修改频率只由已读历史支持。

## S10 发散式变化 · Divergent Change

- **定义：** 一个模块因多种彼此独立的业务或技术原因需要修改，变化轴没有得到合理分离。
- **候选信号：** 同类同时实现税费规则、数据库格式与页面布局；不同需求触及不同方法簇。
- **必要证据：** 标明至少两种具体且独立的变化原因，以及对应实现。仅“类做很多事”不足，说明规则归属与变化轴；历史可补强但非必需。
- **合理例外：** 仅协调委托的用例服务、边界清楚的门面、同一领域规则不可分的步骤；多个方法不意味着不同变化轴。
- **维护影响：** 改一个方向需要理解同模块内无关约束，增加冲突或回归范围。
- **改善方向：** 按变化原因提炼职责，保留统一协调入口。
- **上下文不足：** 只有方法名或片段时，查实现和调用约定，不能把假设的变化原因当成事实。

## S11 霰弹式修改 · Shotgun Surgery

- **定义：** 同一知识或责任分散到多个独立位置，一项规则改变就需同步修改。
- **候选信号：** 相同门槛、校验或映射在多个入口独立实现；同一需求的字段传播靠多处人工维护。
- **必要证据：** 对照至少两个实际位置，确认表达同一规则，解释具体变更为何需要同步修改。多文件改动、相同常量或相似代码本身不充分。
- **合理例外：** 合理分层的声明／实现／测试更新；独立部署边界下有明确版本协议的复制；数值相同但含义不同。
- **维护影响：** 规则不一致、遗漏修改；若只是潜在风险明确标记，不编造历史遗漏。
- **改善方向：** 集中规则或移动职责，边界间用合适契约同步；避免强耦合原本独立的模块。
- **上下文不足：** 只有一个位置、规则含义未知或第二处未见时，不断言同步修改必要，说明需比较的入口。

## S12 平行继承体系 · Parallel Inheritance Hierarchies

- **定义：** 两套继承体系的类型扩展必须一一配套，增加一个子类会强制增加另一套子类。
- **候选信号：** 类型名前缀配对、双重注册表、一套子类构造另一套对应子类。
- **必要证据：** 查看两个体系、构造／注册连接与扩展契约，证实配套要求。仅有相似命名或两棵树不充分。
- **合理例外：** 编译生成的镜像协议、清楚且不可消除的格式矩阵、彼此独立且无强制配套关系的继承树。
- **维护影响：** 新类型需要协调两套体系，配对遗漏或组合规模增加。
- **改善方向：** 用对象关联、组合、数据映射或单一扩展点消除无意义的重复类型维度；不要破坏确有价值的独立扩展轴。
- **上下文不足：** 缺少配对构造或注册约定时保留判断，追踪相似名字不足以结束核查。
