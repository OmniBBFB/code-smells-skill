# 全量版评估与已知限制

日期：2026-10-01。当前规则覆盖 S01—S23，分为六组引用文件。本次验证规则和工作流的可执行性，不声称能检出所有代码中的所有坏味道。

## 验证材料

- 69 个原创 Python 静态案例：每项一个正例、合理反例和信息不足例。原有 12 例作为回归材料，新增 57 例。
- 一个跨文件小型应用：指定购物车、支付和生命周期三处入口，允许按需追踪钱包定义、仓库约定和事件注册。
- 8 个评分器行为测试：覆盖相关标签、负例误报、发现／不确定区分、缺失字段、非法标签、缺失与重复案例。

案例语法均通过编译检查；业务代码未执行。测试集包含明确的契约说明，使证据可核实；真实仓库通常更模糊。它们是合成案例，不是代表性的实际项目抽样，也没有独立保留的长期未见测试集。

## 独立评估方法

首轮将 69 例固定种子打乱，分为三批，每批 23 例。各 agent 仅看到匿名代码、skill 及必要引用，不能访问答案、其他批次或主会话。任务统一要求检查 23 类，允许无发现、同根因合并和上下文不足判断。

保留首轮实际使用的 skill 快照、匿名输入、映射、原始 JSON、报告与评分。快照入口命名为 `SKILL.snapshot.md`，避免客户端将评估目录递归发现为重复技能。主 agent 对照源代码复核了确定发现的证据、位置、影响和建议，并核对全部69个片段与评估前生成源一致。

对差异项使用新隔离目录和独立 agent 复测，保留每轮输入和输出；没有把答案给评估者。工作流验证独立完成，核实必要上下文是否被实际读取、DTO与注册回调是否被误报，以及审查范围是否被说明。

## 首轮结果与修订依据

精确主标签评分 **66/69**：正例22/23、反例23/23、信息不足21/23。

| 差异 | 实际输出 | 修订与处理 |
|---|---|---|
| 大类正例 | S10；证据文字明确同时支持 S02 | 同根因允许主／相关标签；随后复测暴露 S02 将调用者当硬前置的歧义，改为完整实现足够时可直接判断 |
| 霰弹式修改信息不足例 | S14 信息不足，理由已指出共同演进契约缺失 | 两类同根因候选可明确相关标签；评分器识别相关标签，并保留主标签统计 |
| 基本类型偏执信息不足例 | 只形成 S22 转发候选 | 原样例只有一次无约束转发，不足以稳定形成 S03 候选；加入两处原始值校验与成组传递，仍不提供领域／协议归属，作为修订后的信息不足例 |

首次复测的分类字段混入中文名称，评分器拒绝该 schema；原始输出保留于 `retest-attempt-1`。这是评估输入／输出协议问题，不把 skill 的正常中文报告强制改为机器格式。

第二次复测按纯编号输出，三个目标为2/3：重复与原始值候选正确保留判断，但大类被保留为候选。复核发现“阅读成员及相关调用者”的文字容易被理解为固定前置条件，忽略完整类中已直接展开的独立职责。修订 S02，明确调用者在边界仍不清楚时才是补证要求；门面例外要求职责实现已经委托，而不只看统一入口或方法名。

同时将报告约束收紧为“只为有可观察信号的候选说明证据缺口”，避免因为缺少所有领域资料而泛列不确定项。评分器未放宽必要证据；相关分类需要人工复核，不能靠添加所有标签提高分数。

S02 修订后用大类正例、门面反例和只有声明的片段独立回归，**3/3**：确认 S02并合并S10，排除协调门面，信息不足时保留判断。


```bash
python3 evals/score.py --expectations evals/full-expectations.json --mapping evals/runs/full-final/mapping.json --results evals/runs/full-final/results.json --output /tmp/code-smells-full-score.json
```

